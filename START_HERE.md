## 1. Что это за проект

Живая система, которая для теннисного матча в реальном времени оценивает
вероятность того, что подающий удержит **следующий, ещё не начавшийся** гейм, а
позже — распределение точного счёта этого гейма (8 исходов: 40-0, 40-15, 40-30,
с ровно, и то же со стороны брейка).

**Чем это НЕ является.** Это не машина для денег. Формулировка задачи с самого
начала: исследование плюс paper trading. Причина не в осторожности, а в
измерении — см. пункт 2: на рынке точного счёта требуемое преимущество уже
посчитано и оно больше нашей собственной точности. Любой документ или человек,
который обещает здесь стабильный доход, противоречит числам в этом репозитории.

**Текущая фаза.** Исследование закрыто, идёт стройка. Всё, что можно было
посчитать на исторических данных, посчитано; всё остальное узнаётся только
записью живых данных.

## 2. Числа, которые надо знать раньше, чем что-то менять

Все получены на реальных данных, не из литературы. Log loss — на прогноз
удержания следующего гейма, мужская сетка Grand Slam, тест 2019–2024,
66 697 сервисных геймов.

| Что | Сколько | Смысл |
|---|---|---|
| Elo-приор вместо грубого | **+0.0123** | главный и почти единственный рычаг |
| Накопленная статистика подачи в матче | +0.0030 | второй по величине |
| Сторона принимающего | +0.0005 | есть, но мало |
| Исходы предыдущего гейма | +0.0001 | **ноль**, интервал через ноль |
| Процессные признаки Hawk-Eye (скорость подачи, длина розыгрыша, пробег) | **−0.0001** | **ноль.** Это закрыло всю видео-ветку |
| Ошибка приора после вычета биномиального шума | 5.5 п.п. на туре, 6.4 на Challenger | по вероятности очка |
| То же в вероятности удержания гейма | 10 и 13 п.п. | множитель dP(hold)/dp = 1.92 при p = 0.62 |
| Остаток ошибки после 40 очков внутри матча | 4.5 п.п. | live-статистика уменьшает, но не убирает |
| Маржа: точный счёт гейма | **20.0 % BetBoom**, 25.0 % Пари | поток; июльский скриншот давал 19.9 % — сошлось |
| Маржа: победитель следующего гейма (2 исхода) | **11.82 %** | 171 наблюдение; WTA 11.89 %, WTT/ITF 7.99 % |
| Какой гейм котирует контора | **следующий, 74 % случаев** | ровно то, что мы моделируем |
| Точность самой конторы | **~1–2 п.п.** | два её рынка на одном гейме расходятся на 1.09 |
| Требуемое преимущество на точном счёте гейма | **7.1–10.0 п.п. по вероятности очка** | по измеренной марже 20 %; раньше стояло 5.1 — устарело |
| Расхождение двух контор в оценке p | 1.6 п.п. | **против нашей ошибки 5.5** |
| Лимиты контор | не ограничение: потолок **выплаты** 1.5 млн ₽ BetBoom, 3.5 млн ₽ Пари | не потолок ставки |

**Два вывода, на которых держится всё остальное.**

Первый: на точном счёте гейма требуемое преимущество (7.1–10.0 п.п. по
измеренной марже 20 %) **превышает** нашу полную неопределённость (5.5). Рынок
закрыт количественно. На двухисходном «победителе следующего гейма» требуется
4.2–6.0 на туре и **2.8–4.0 на WTT/ITF** — и только там требование ниже нашей
ошибки. Это единственная незакрытая ставочная гипотеза.

Второй, и он неприятнее: две независимые конторы расходятся в оценке p на
1.6 пункта, а два рынка **одной** конторы на одном гейме — на 1.1 пункта. То
есть её точность порядка одного-двух пунктов, а наша 5.5: она точнее нас в
три-пять раз. Любая схема, которая начинается со слов «наша модель увидит
раньше рынка», обязана сначала объяснить это расхождение. Честная формулировка
оставшейся гипотезы не «мы обгоним рынок», а «на нижних уровнях контора может
деградировать быстрее нас» — и это проверяется только записью.

## 3. Что закрыто и не строится

Не возвращаться к этому без нового измерения. Каждый пункт закрыт расчётом или
экспериментом, обоснования — в аудите.

- **Видео и computer vision.** Процессные признаки Hawk-Eye дали ноль у обоих
  полов, в подвыборке с трекингом и отдельно без приора. Если самые чистые
  процессные данные, какие существуют, не дают ничего, то распознавание позы с
  трансляции тем более.
- **Мультиагентные дебаты (MAD), агенты-спорщики.** Нечего обсуждать: вся
  информация сводится к одному числу p.
- **RAG по соцсетям и новостям.**
- **Отдельная модель точного счёта.** Все 8 исходов — функция одного p.
  Проверено четырьмя независимыми сверками с реальными книгами, максимальное
  расхождение 0.014.
- **Машина состояний NORMAL → HOT → DOMINANT.** Заменена непрерывным
  апостериором. Фиксированный порог «расхождение 5 очков» срабатывает на
  68–78 % геймов из одного шума.
- **Momentum как отдельный признак.** Движение цены после проигранного очка —
  чистая марковская механика, а не «рынок что-то узнал». Это был центральный
  пример исходного блюпринта, и он опровергнут расчётом.

## 5. Локальная установка

Python 3.11 или новее.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m pytest tennis/ -q
```

**В PowerShell активацию лучше не делать вообще.** `Activate.ps1` падает с
`PSSecurityException` на машине, где не разрешён запуск скриптов, а это состояние
по умолчанию. Вместо этого зови интерпретатор venv напрямую — он тот же самый:

```powershell
cd путь\к\mily            # именно в корень репозитория, иначе не найдётся requirements.txt
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m pytest tennis/ -q
```

Команды вводить **по одной**. Вставленный блоком многострочник PowerShell
склеивает через `>>` и выполняет не так, как ожидаешь — на этом уже потеряли
один заход.

Ожидаемый результат: **405 прошло, 1 пропущен.** Один пропуск — это весь модуль
тестов рекордера сразу (пять тестов), ему нужны сгенерированные классы protobuf.
Они собираются локально и лежат в `.gitignore`:

```bash
mkdir -p tennis/ingest/betboom/generated
python -m grpc_tools.protoc -I tennis/ingest/betboom/proto \
    --python_out=tennis/ingest/betboom/generated \
    tennis/ingest/betboom/proto/bb_sport_ws_v1.proto
python -m pytest tennis/ -q
```

В PowerShell то же одной строкой — перенос через `\` там не работает, а `mkdir`
и так создаёт промежуточные каталоги:

```powershell
mkdir tennis/ingest/betboom/generated
python -m grpc_tools.protoc -I tennis/ingest/betboom/proto --python_out=tennis/ingest/betboom/generated tennis/ingest/betboom/proto/bb_sport_ws_v1.proto
python -m pytest tennis/ -q
```

После этого — **410 прошло, 0 пропущено.** Проверено 22.09.2026: и сборка, и
оба прогона.

Многострочные команды в остальных документах написаны для bash. В PowerShell
переносить их надо либо в одну строку, либо через обратную кавычку `` ` `` вместо
`\`. На этом уже спотыкались.

### Про VS Code конкретно

- **Интерпретатор.** Ctrl+Shift+P → «Python: Select Interpreter» → путь
  `.venv\Scripts\python.exe` внутри репозитория (не системный Python и не venv,
  случайно созданный уровнем выше). Без этого тесты в панели Testing не найдутся.
- **`import tennis` работает из корня** благодаря `conftest.py`, который кладёт
  корень репозитория в `sys.path`. Запускать pytest надо из корня, не из
  подкаталога.
- **Панель Testing** настроена заранее: в репозитории лежит
  `.vscode/settings.json`, где pytest включён и нацелен на `tennis`. Если тесты
  всё равно не видны — выбери интерпретатор и нажми Refresh Tests.
- Русский текст в документах — UTF-8, никаких настроек не требует.

## 7. Где мы в плане

### Трек A: коллектор. Стоит ноль, стартует первым

1. **Рекордер BetBoom** — написан. Линия идёт только по WebSocket в protobuf,
   дельта-подписка. **Тот же сокет отдаёт счёт и сторону подающего**, то есть
   котировка и состояние приходят парой из одного источника с одной метткой
   времени. Схема восстановлена из JS-бандла, не подключаясь к серверу.
2. **Append-only лог** — написан.
3. **Живые сессии проведены** — 22.09.2026, две. Первая (с машины владельца)
   нашла два дефекта протокола: дерево ленивое, а `settings_set` сервер
   отвергает. Вторая (из песочницы агента, после починки) закрыла все
   неизвестные: 10 одновременных подписок держит; гейм-рынки есть везде, но
   **точный счёт гейма — только от Challenger и WTA 125 и выше**, на WTT/ITF
   лишь двухисходный «Исход»; рукопожатия сверх подписки не требуется.
4. **Движение цены внутри гейма пишется** — с 22.09.2026. Полный снимок идёт
   на смену счёта, а не по таймеру, поэтому переоценка во время розыгрыша в
   него не попадала: измерено опережение потока `newsletters_stake` — медиана
   0.5 с, p90 78 с, максимум 153 с, и одно изменение снимок не показал вовсе.
   Рекордер теперь шлёт `stakes_subscribe` (203 исхода, 1015 пушей за 5 минут
   на боевом прогоне). Подробности — в `docs/TRACK_A_betboom_capture.md`.
5. **Платный PBP-фид** — уже не для сшивки, а только для измерения абсолютной
   латентности: кто раньше видит очко, корт или контора.
6. **Измерить абсолютную латентность** на 20–50 матчах. **Это число решает,
   существует ли проект как live-система.** Ждёт решения по бюджету, которое
   сам план откладывает до конца первой недели записи.

### Трек B: движок. Параллельно

1. **Модуль `markov/`** — ГОТОВО.
2. **Оффлайн-джоб рейтингов** — СЛЕДУЮЩЕЕ. `build_elo` и `rolling_priors` из
   `research/elo_prior.py` с сериализацией состояния, чтобы live-процесс поднимал
   рейтинги, а не перемалывал 270 тысяч матчей. Конфигурация из свипа: K = 400,
   экспонента 0.4, вес покрытия 0.3, смесь 0.6 на Elo.
3. **Snapshot builder + тест на утечку** (подменить все события после снимка
   мусором, прогноз не должен измениться).
4. **Live-состояние**: байесовское обновление четырёх величин по очкам,
   начать с бета-биномиального.
5. **Остаточная модель + калибровка** на out-of-time.
6. **Replay-бэктест** строго по `ts_received`.

## 8. Первое, что надо сделать

Строго по приоритету.

1. **Запустить запись всерьёз** — с машины, которая не исчезает. Разведка
   закончена, рекордер работает, потолок подписок ≥ 10, лог сжимается.
   Каждый день без записи — безвозвратно потерянный день: гейм-рынок живёт
   около минуты и не архивируется никем.
   ```powershell
   .venv\Scripts\python.exe -m tennis.ingest.betboom.client --out data/raw --max-matches 10
   ```
   Оставить работать надолго. Занимает 0.3–0.9 ГБ в сутки, переживает обрывы
   связи (переподключение с нарастающей паузой), новый день пишет в новый файл.
   Остановить — Ctrl+C, он допишет концевик и напечатает отчёт.

   **Лучше всего — на отдельной Linux-машине:** `bash deploy/vps-setup.sh`
   ставит всё с нуля (проверено от чистого клона), а
   `deploy/betboom-capture.service` делает из этого службу, переживающую
   перезагрузку. Ноутбук — плохой дом: он спит, его закрывают, его увозят.

   Если всё же на ноутбуке — **в отдельном окне PowerShell,** не в фоне сессии
   агента и не во встроенном терминале редактора: и то и другое умрёт вместе с
   сессией. Записи
   не нужен ни ИИ, ни агент — это обычная программа, и стоит она ноль.
   Погашенный экран записи не мешает, **сон машины — останавливает**
   (`powercfg /change standby-timeout-ac 0` и «действие при закрытии крышки —
   не требуется»). Подробности в `docs/TRACK_A_betboom_capture.md`.

   Разовые проверки и разбор протокола можно делать из сессии агента — сокет
   через прокси проходит, вопреки тому, что было записано раньше.
2. **Сверить `APP_BUILD`** в `runtime-env.js` конторы перед каждым запуском.
   Номера полей protobuf — это контракт, и молчаливая перенумерация испортит

## 10. Грабли, на которые уже наступили

Это самая полезная секция файла. Каждый пункт — реальный баг или ошибка, которая
стоила времени и в двух случаях **переворачивала вывод**.

**Баги в коде, найденные и исправленные.**

- `invert()` возвращал baseline для каждой вероятности ниже 0.5 — половина всех
  значений была мусором. Бисекция искала только `d ≥ 0`, а самопроверка брала
  лишь 0.5, 0.6, 0.75 и 0.9 и ничего не заметила. **Это перевернуло главный
  вывод эксперимента B1.** Теперь прибито тестом round-trip от 0.05 до 0.95.
- Сетка (мужская/женская) определялась по тому, присоединился ли ATP-приор, а AO
  и RG за 2018–2021 сокращают имена. 762 мужских матча (26 679 геймов) попали в
  женскую выборку, а мужской тест потерял AO и RG целиком. Лечение: сетка из
  третьего сегмента `match_id`, имена нормализуются в «инициал + фамилия».
- Токен `GAME` в RG-2020, AO-2021 и RG-2021 читался как признак тайбрейка →
  ~1500 матчей выброшено молча.
- Sackmann ставит всем матчам турнира дату его начала, поэтому join приоров по
  (игрок, дата) раздул 406 920 строк до 3 088 401. Лечение: ключ по уникальному
  `match_key` и окна по строго более ранним турнирам.
- Битый `ElapsedTime` давал `sec_per_point` до 1e26. Признаки при этом
  **улучшали AUC и ухудшали log loss** — это подпись взрыва калибровки от
  выбросов, а не находка.
- Заполнение пропусков нулями смешивает «отклонения нет» и «не измерено».
  Лечение: винзоризация по перцентилям обучающей выборки плюс явные индикаторы
  пропуска.
- Baseline (`tour_spw` и средние по году/покрытию) считался по всей выборке,
  включая тест. Утечка. Лечение: baseline предыдущего года.
- Условие «без приора» в confound-тесте всё равно протаскивало приор через
  `live_spw_dev` (сжатие к `p_prior`, потом вычитание `p_prior`). Лечение:
  отдельный prior-free блок со сжатием к константе C = 0.62.
- `build_games` работал 700+ секунд процессорного времени на миллионах мелких
  вызовов pandas. Переписан одной векторной `groupby.agg` → 11 секунд.

**Ошибки в арифметике документов, исправленные.**

- Множитель чувствительности был написан 2.6 при собственной вычисленной
  производной 1.92 — все производные числа были завышены примерно на треть.
- Отношение шума Challenger к туру было заявлено «1.5×» при подстановке общего
  биномиального шума вместо поуровневого. Правильно 1.16.
- «14 конфигураций» на самом деле было 18.

**Ловушки идентификации.**

- Три исхода с одной стороны определяют p только с точностью до `p ↔ 1−p`:
  `h30/h15 = 2.5q` — зеркало `b30/b15 = 2.5p`. Первая попытка дала вероятности
  удержания 7–25 %, что невозможно. Лечение: ограничение `p ≥ 0.5`.

**Операционные.**

- `pkill -f elo_prior.py` дважды убивал собственную оболочку, потому что шаблон
  совпадал с текстом самой команды. Сканировать `/proc/*/cmdline`.
- Четыре оригинальных репозитория данных Sackmann удалены с GitHub в июне–июле
  2026. Живёт зеркало `Aneeshers/tennis-sackmann-archive`. **Датасетов сейчас
  нет на диске** — контейнер пересоздан. Чтобы пересчитать RMSE 0.0871/0.0855,
  их надо скачать заново; команды в `docs/EXPERIMENT_B_...`. Пока эквивалентность
  ядра исходнику держит `tennis/markov/tests/test_equivalence.py`.
- PowerShell подменяет `curl` на `Invoke-WebRequest`, поэтому bash-синтаксис с
  `\` и `| head -c` там не работает. Нужен `curl.exe` одной строкой.
- Фильтр вида спорта по подстроке «теннис» подписал рекордер на Setka Cup —
  настольный теннис, чьё дерево пришло первым и заняло все слоты. Совпадение
  слага должно быть точным (`tennis`, id 4).
- «Прокси песочницы не пропускает WebSocket» — было записано как измеренный
  факт и оказалось **неверным**: `101 Switching Protocols` проходит, кадры идут.
  Из-за этого разведка протокола ждала чужой машины, хотя могла идти сразу.
  Урок: «не работает» — это результат конкретной команды с конкретным выводом,
  а не вывод из документации прокси.
- Рекордер, который печатает только при ошибке соединения и раз в 200
  котировок, при нуле котировок молчит — и не отличим от зависшего. Любой
  долгоживущий процесс обязан иметь сердцебиение.
- Три типа ответов из 32 обрабатывались, остальные молча выбрасывались, в том
  числе `error` и `code ≠ 200` внутри типизированных ответов. Первая живая
  сессия из-за этого выглядела как «сокет пустой», хотя сервер в ответах
  называл и ошибку, и виноватое поле.
- `.venv\Scripts\Activate.ps1` падает с `PSSecurityException`, если запуск
  скриптов не разрешён — а это состояние Windows по умолчанию. Политику менять не
  нужно: `.venv\Scripts\python.exe` работает и без активации.
- Многострочные команды, вставленные в PowerShell блоком, склеиваются через `>>`
  и выполняются не по одной. Плюс отдельная классика: запуск из родительского
  каталога вместо корня репозитория даёт `Errno 2` на `requirements.txt` и venv
  не в том месте.

**Две мои ошибки, которые стоит знать, потому что они про суждение, а не про код.**

- Я сказал, что история ставок за июль «почти ничего не даст». Неверно: из неё
  вышли 17 одновременных снимков рынка и самая полезная находка той сессии.
- Я написал в тесте по памяти, что 4-пунктовое преимущество на подаче даёт
  больше 75 % на матч. Пересчёт: 69.1 %. Тест теперь утверждает структурный факт
  (преимущество строго растёт по иерархии: 0.040 очко → 0.070 гейм → 0.130 сет →
  0.191 матч), а не запомненное число.

## 11. Честно про риски

**Правовое и аккаунты.** Автоматический сбор почти наверняка противоречит
пользовательскому соглашению конторы, а аккаунты, показывающие прибыль,
ограничивают. Это решение владельца проекта, а не техническое ограничение. Стоит
держать в голове, что **запись публично отображаемых котировок и реальная игра с
того же счёта — разные по величине риски**.

**Защита сайта.** Перед BetBoom стоит QRATOR, плюс антифрод Group-IB (`/api/fl`,
ротация токена `cfids` каждые несколько секунд). На самом фид-сокете они не
наблюдались, но закладываться на это нельзя. Домен конторы и зеркала ротируются,
поэтому в коллекторе он должен читаться из конфига, а не быть вшит.

**Безопасность.** В одном из загруженных в сессию файлов лежал сессионный токен
1win открытым текстом. Он больше не нужен ни для чего (их API публичный, хватает
партнёрского id), и ту сессию стоит перелогинить. Токены в репозиторий и в чат
не кладём.

**Критерий остановки проекта.** Если после 5 тысяч прогнозов с синхронными
котировками разница с рынком неотличима от нуля ни в одном сегменте — гипотеза
про опережение рынка отвергнута. Тогда ценность проекта в другом: калиброванная
модель состояния игрока и объяснения, без ставочной составляющей. Это
заранее принятое условие, а не поражение.

`code ≠ 200`, и что лежит внутри первого кадра каждого типа. Один раз это уже
спасло: сессия выглядела зависшей, а в логе сервер прямым текстом называл и
ошибку, и поле, которое отверг.
