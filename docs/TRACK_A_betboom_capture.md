# Трек A: как записывать гейм-рынки BetBoom

**Дата:** 22 сентября 2026 • **Ветка:** `claude/tennis-prediction-audit-kskn26`
**Код:** `tennis/ingest/betboom/`, `tennis/ingest/rawlog.py`

## Вопрос

До кода и до бюджета надо было ответить на один вопрос: **как получить гейм-рынки
BetBoom в объёме тысяч наблюдений.** Без этого коллектор собирал бы статистику
матчей без котировок, а нужна пара. Ручные снимки этого не решают: за июль их
накопилось 17, и все сделаны в моменты, которые игрок выбрал для ставки, а не
случайно.

## Ответ

Линия BetBoom отдаётся **только по WebSocket, протоколом protobuf**, и это
**подписка, а не опрос**: после `matches_subscribe_full` сервер сам присылает
полный снимок рынков матча при каждом перепрайсинге. Записывать её — задача
удержания сессии, а не частоты запросов. Тысячи наблюдений набираются сами:
измерено, шесть живых матчей дают 27 снимков по 140–182 котировки за минуту.
(Первая редакция этого документа называла фид «дельта-подпиской с сообщением на
каждую цену» — это было прочитано из схемы, а не измерено, и оказалось неверно.)

Схема протокола **полностью восстановлена** и лежит в репозитории.

## Что установлено

### Букмекерский движок — не BetBoom

`betboom.ru` это витрина. Ставочная часть — вайт-лейбл платформы **sporthub.bet**.
Из конфигурации фронта (`runtime-env.js` виджета):

| Параметр | Значение |
|---|---|
| `FEED_WS_URL_TEMPLATE` | `wss://{partner}-ws2.sporthub.bet:443/api/tree_ws/v1` |
| `FEED_WS_PROTOCOL` | `protobuf` |
| `MAX_MATCHES_SUBSCRIBE_FULL_ITEMS_LIMIT_PER_REQUEST` | **1** |
| `MAX_MATCHES_SUBSCRIBE_ITEMS_LIMIT_PER_REQUEST` | 50 |
| `APP_BUILD` | `8.45.1-5d29aa45` |

HTTP-дублёра линии нет. Проверено прямо: при заблокированном сокете страница
`betboom.ru/sport/live` отдаёт 200 и рендерит только навигацию — ни одного
события, ни одного коэффициента.

### Схема протокола восстановлена из клиента

Клиент собран на protobuf-es v1, который компилирует каждое сообщение в
литеральный список полей прямо в JS-бандл. Это делает формат провода полностью
восстановимым, ни разу не подключившись к сокету.

`tennis/ingest/betboom/extract_schema.py` разбирает бандл и выдаёт `.proto`:
**223 сообщения, 1012 полей, 25 перечислений.** Файлы лежат в
`tennis/ingest/betboom/proto/`. Проверка: `protoc` компилирует их без ошибок,
запрос подписки и push-обновление котировки проходят round-trip
(`tennis/tests/test_betboom_client.py`).

### Что несёт котировка

`ModelsStake` — ровно та строка, которую надо писать:

```proto
string stake_id = 1;      int64  match_id = 2;
bool   is_active = 3;     bool   is_live = 4;
string name = 5;          int64  outcome_id = 7;
double factor = 10;                     // коэффициент
int64  market_id = 13;    string market_name = 14;
int64  group_id = 17;     string group_name = 18;
string period_name = 20;  optional string period_id = 22;
```

`market_name` + `period_name` адресуют рынок с точностью до гейма — то есть
«победитель следующего гейма» и «точный счёт гейма» различимы и привязываются к
конкретному гейму конкретного сета. `is_active` показывает, **когда контора
сняла рынок**, а это само по себе измерение: момент снятия и момент возврата с
новой ценой — прямая метка перепрайсинга.

### Счёт приходит из того же сокета

Это снимает главное возражение «будет статистика без котировок».
`ModelsMatch.MatchInfo` содержит:

- `scoreboard.serving_side` — перечисление `HOME / AWAY`, **кто подаёт**;
- `scoreboard.scores[]` с типом `SCOREBOARD_SCORE_TYPES_GAME` — счёт внутри гейма;
- `period_scores[]` с `is_current` — сеты и текущий период;
- `is_bet_stop` — заморозка матча целиком;
- `provider` (`DIGITAIN / ODDIN / SPORTRADAR / LSPORTS`) и `provider_id` —
  **чей фид использует сама контора** и его идентификатор матча.

Последнее особенно ценно. Во-первых, известно, с кем мы соревнуемся по скорости.
Во-вторых, `provider_id` даёт готовый ключ для сшивки с независимым PBP-фидом —
сопоставлять по именам игроков не нужно.

### Транспорт и поведение

Подписка выглядит так:

1. ~~`settings_set` (язык)~~ — сервер отвергает его без `time_filter` (400),
   и он не нужен: дерево и так приходит по-русски;
2. `state_subscribe_by_sports{types:[LIVE]}` → виды спорта **со счётчиками, без
   турниров**;
3. `state_subscribe_sports{sport_id=4, type=LIVE}` → всё дерево тенниса одним
   ответом (~100 КБ), и дальше `newsletters_match` по **каждому** живому матчу
   вида спорта — счёт, сторона подающего, статус, основные котировки;
4. `matches_subscribe_full{match_id}` — по одному матчу на запрос; в ответ
   полный снимок всех рынков матча;
5. дальше `newsletters_full_match{action=UPDATE, match}` — **снова полный
   снимок** всех рынков при каждом перепрайсинге, примерно раз в 13 секунд на
   матч, между снимками меняется от 22 до 137 цен из ~180. `newsletters_stake`
   за минуту на шести матчах не пришёл ни разу; возможно, его даёт отдельный
   `stakes_subscribe`, но для записи он и не нужен.

Полный набор исходов приходит одним снимком, поэтому **overround считается
непрерывно**, а не по скриншоту. Оба измерения из июля (19.9 % и 25.0 %)
становятся распределением вместо двух точек.

## Что это меняет в плане

Трек A в HANDOFF начинался с выбора PBP-фида, а котировки шли вторым пунктом.
Порядок надо поменять:

1. **Сначала рекордер BetBoom.** Он единственный даёт данные, которых нет нигде
   и которые нельзя получить задним числом. И он же отдаёт счёт со стороной
   подающего, то есть пару «котировка + состояние» из одного источника с одной
   меткой времени.
2. **Платный PBP-фид — потом, и с другой целью.** Не для сшивки с котировками
   (она уже есть), а только для измерения латентности: кто видит очко раньше,
   мы или контора. Это отдельный вопрос, и он не блокирует запись.
3. **Бюджет на данные перестаёт быть входным условием.** Первый этап стоит ноль.

## Первая живая сессия: 22.09.2026, 206 секунд

Сокет открылся с первой попытки, 51 кадр лёг на диск. Подписок — ноль, и
рекордер об этом не сказал ни слова. Разбор сырого лога (`inspect_log.py`)
дал три факта, каждый из которых менял код:

1. **`settings_set` отвергнут:** `code=400`, «Данные не прошли валидацию»,
   нарушение в поле `time_filter`. Это строка без перечисления в схеме, и что в
   неё класть — неизвестно. Но дерево пришло `code=200` без неё, и уже
   по-русски. Вызов теперь пропускается, если `--time-filter` не задан.
2. **Дерево ленивое.** `state_subscribe_by_sports` вернул 16 видов спорта с
   одними счётчиками: теннис `id=4`, `matches_count=62`,
   `tournaments_count=28` — и ни одного турнира внутри. Рекордер читал
   `sport.tournaments` и находил пустоту. Слои надо запрашивать по очереди:
   `state_subscribe_by_categories{sport_id}` → категории с турнирами →
   при необходимости `state_subscribe_categories` и
   `state_subscribe_tournaments` → матчи → `matches_subscribe_full`.
3. **Слои приходят и пушами:** `newsletters_sport` (25 штук за сессию),
   `newsletters_category`, `newsletters_tournament`, `newsletters_match`. Теннис
   пришёл именно так, а не в ответе на подписку. Оба пути теперь ведут в одни
   обработчики.

Отдельно закрыт пробел в диагностике: отказ приходит **внутри** типизированного
ответа (`code`/`status`/`error`), а не только верхним `error`, и раньше на это
никто не смотрел. Теперь любой `code ≠ 200` печатается с сообщением и именем
поля из упакованных деталей.

## Вторая живая сессия: из песочницы агента, 22.09.2026

Раздел ниже («Где это должно работать») утверждал, что рекордер не может идти
из песочницы, потому что прокси не пропускает WebSocket. **Это оказалось
неверно.** Прямая проверка: `CONNECT ru-ws2.sporthub.bet:443` через прокси →
`HTTP/1.1 101 Switching Protocols`, дальше кадры идут в обе стороны. Полный
цикл — дерево, подписка на теннис, полные рынки по десяти матчам — отработал
из песочницы за секунды. Что это меняет: разведку протокола и любые разовые
замеры можно делать прямо из сессии агента; отдельная машина нужна только
для многочасовой записи, потому что контейнер сессии живёт недолго.

### Протокол: две поправки к первой сессии

1. `state_subscribe_by_categories` — путь **только для киберспорта.** Сервер
   принимает в нём единственный `sport_id = 1` («Кибер») и возвращает
   категории Dota 2, CS2, R6, Мир танков. Для обычного вида спорта он отвечает
   `400`, и именно это остановило первую починку.
2. Обычный вид спорта подписывается через `state_subscribe_sports` с элементом
   `{uid, type = LIVE, sport_id}`. **Ответ и есть всё дерево:** 99 705 байт для
   тенниса, 27 турниров, 68 матчей, в поле `sports[].sport`. Дальше идут пуши
   `newsletters_match` — 33 штуки за 14 секунд.

3-е, 4-е, 5-е очко гейма.

### Как адресуется гейм

Для гейм-рынков `period_name` **пуст**, а `market_name` несёт всё:
`«2-й сет 6-й гейм: Точный счёт»`, `«3-й сет 11-й гейм: Исход»`. Исходы точного
счёта называются `П1:0`, `П1:15`, … ; у «подающего или брейка» — `П:0`, `П:15`, …
Разбор `market_name` регулярным выражением `(\d+)-й сет (\d+)-й гейм: (.+)` —
это первое, что должен делать модуль `market/`.

Флаг `is_active` работает как описано: у уже невозможных исходов (`6:0` при
идущем сете) он `false` при сохранённой цене.

### Счёт из того же сокета — уточнение полей

`scoreboard.serving_side`: `HOME = 1`, `AWAY = 2`. `scoreboard.scores[]` — это
`{type, sequence, home_score, away_score}`, а не строки. `period_scores[]` с
`is_current`. `provider_id = 'sr:match:74929514'` — идентификатор **Sportradar**:
контора сидит на его фиде, и это готовый ключ для сшивки с любым другим
источником, где он есть.

### Объём записи

Измерено на шести матчах за 60 секунд: **234 кадра, 1 539 641 байт** на плотной
выборке (WTA, ~180 рынков на матч). Это ~92 МБ в час и ~2.2 ГБ в сутки; на
десяти матчах — около 3.7 ГБ. Почти всё — повторяющиеся полные снимки: base64
поверх protobuf с одними и теми же именами рынков.

**Сжатие включено, измерено на живой записи.** `rawlog` пишет `.jsonl.gz`:
каждому `fsync` предшествует `Z_SYNC_FLUSH`, поэтому построчная гарантия при
падении сохраняется, а словарь deflate не сбрасывается и сжатие почти не
страдает.

| Выборка | Распакованный | На диске | Раз | В сутки на диске |
|---|---|---|---|---|
| WTT, 6 матчей, 60 с (живая запись) | 602 КБ | 126 КБ | **4.8×** | **0.18 ГБ** |
| WTA, 6 матчей, 60 с (тот же лог, gzip одним проходом) | 2 130 КБ | 394 КБ | **5.4×** | 0.55 ГБ |

То есть десять матчей круглосуточно — порядка **0.3–0.9 ГБ в сутки** вместо
2–4 ГБ. `--no-compress` оставлен для случая, когда лог надо читать глазами
или `grep`-ом.

Читатель прозрачно ест оба формата; искать файлы нужно через
`tennis.ingest.rawlog.find_logs`, а не `rglob("*.jsonl")` — иначе сжатая
запись становится невидимой.

Счётчик `stake updates` в отчёте рекордера считает каждую котировку каждого
снимка, поэтому «400 обновлений за минуту» — это два-три снимка, а не четыреста
перепрайсингов.

### Что осталось

Ничего блокирующего, и ничего обязательного до старта записи: gzip сделан,
запись можно включать. Дальше по порядку: парсер `market_name` в
`(сет, гейм, вид)`; разностный разбор соседних снимков — какие именно цены
сдвинулись и когда; overround двухисходного рынка на потоке (пока одно
наблюдение — 9.9 %); запись хотя бы одного матча целиком от первого гейма до
последнего; латентность против перепрайсинга по `is_active`/`is_bet_stop`.

## Где это должно работать

Первоначально здесь стояло «не здесь»: другая сессия намерила, что прокси не
пропускает WebSocket (`ws_closed_mid_exchange`, 0 кадров в браузере). **Это
опровергнуто прямой проверкой** (см. «Вторая живая сессия» выше): из песочницы
рекордер работает полностью. Разовые замеры — из сессии агента; многочасовая
запись — с машины, которая не исчезает.

Два слоя защиты, которые встретятся: QRATOR перед сайтом и антифрод Group-IB
(`/api/fl`, ротация токена `cfids` каждые несколько секунд). На самом фид-сокете
они не наблюдались, но закладываться на это нельзя.

Отдельно: автоматический сбор почти наверняка противоречит пользовательскому
соглашению конторы, и аккаунты, показывающие прибыль, ограничивают. Это решение
владельца проекта, а не техническое ограничение. Запись публично отображаемых
котировок и реальная игра с этого счёта — разные риски.

## Устойчивость записи

`tennis/ingest/rawlog.py` — append-only лог сырых кадров. Правило: **байты
ложатся на диск раньше, чем кто-либо пытается их понять.** Гейм-рынок живёт
около минуты и не архивируется никем, поэтому ошибка парсера, найденная на
третьей неделе, не должна стоить первых двух. Всё остальное — разобранные
котировки, счёт, таблицы латентности — производное и пересобирается
переигрыванием лога.

Формат JSONL, по строке на кадр: строка это единица, которая при падении либо
целиком уцелела, либо нет, и читатель пропускает оборванную последнюю. То же
на уровне сжатия: убитый процесс оставляет gzip-член без концевика, читатель
доходит до этого места, отдаёт всё предыдущее и останавливается. Parquet —
форма для анализа, собирается позже из закрытых дневных файлов, а не путь
записи.
Каждый кадр несёт `ts_received` и `ts_mono`, плюс `ts_source`, когда провайдер
даёт свою метку: их разность и есть латентность, ради которой всё затевается.

Проверено тестами (`tennis/tests/test_rawlog.py`): дозапись не усекает файл,
оборванная строка не ломает чтение, разбиение по дням идёт по UTC, идентификаторы
событий сортируются по времени.

## Как вести запись сутками

Рекордер — обычная программа без единого обращения к языковой модели. Записи не
нужен ни ИИ, ни агент; запускать её «через ассистента» — значит платить за то,
что процесс сидит и смотрит в сокет.

**Где запускать.** Не внутри сессии агента: фоновый процесс умирает вместе с
ней. Не во встроенном терминале редактора: закрытие редактора его убьёт.
Отдельное окно PowerShell, которое просто стоит открытым:

```powershell
cd C:\путь\к\mily
.venv\Scripts\python.exe -m tennis.ingest.betboom.client --out data/raw --max-matches 10
```

Раз в минуту печатает `[hb]` с числом кадров, подписок и котировок. Обрывы связи
переживает сам, переподключаясь с нарастающей паузой. Остановка — Ctrl+C:
допишет концевик gzip и напечатает отчёт.

**Сон убивает запись.** Погашенный экран — нет, а уход машины в сон — да, и
закрытая крышка ноутбука обычно означает сон. На время записи:

```powershell
powercfg /change standby-timeout-ac 0
```

Действие при закрытии крышки меняется в «Панель управления → Электропитание →
Действие при закрытии крышки» — поставить «Не требуется действий». Вернуть
обратно после записи; проверялось не здесь, а на машине владельца.

**Что переживает перезагрузку.** Ничего из вышеперечисленного. Если нужна
запись, которая поднимается сама, — это Планировщик задач Windows с триггером
«при входе в систему». Пока не настраивалось.

### Только код записи, без документов проекта

На чужой машине незачем держать аудит, исследования и разбор букмекера. Но и
второй репозиторий заводить не надо: правку в `rawlog.py` пришлось бы делать
дважды, и копии рано или поздно разъедутся. Разреженная выборка даёт то же
самое из одного источника:

```bash
git clone --depth 1 --filter=blob:none --sparse <repo> capture && cd capture
git sparse-checkout set --no-cone \
    '/tennis/__init__.py' '/tennis/ingest/**' '/deploy/**' \
    '/requirements.txt' '/conftest.py'
```

Проверено: на диск ложится **340 КБ** — код записи, `deploy/`, зависимости,
и больше ничего. Ни `START_HERE.md`, ни `HANDOFF.md`, ни `docs/`, ни
`research/`, ни `markov/`, ни `market/`. Рекордер из такого клона запускается
и пишет.

Работает это потому, что `tennis/ingest/` ни от чего в репозитории не зависит:
он импортирует только собственные модули. Если это когда-нибудь перестанет быть
правдой, разреженная выборка сломается — и это хорошая причина держать границу.

### Лучше: отдельная машина

Ноутбук для этого плохой дом: он спит, его закрывают, его увозят. Любой
Linux-сервер подходит лучше, и развёртывание на нём проверено целиком —
`deploy/vps-setup.sh` прогонялся от чистого клона до работающего рекордера.

```bash
git clone -b claude/tennis-prediction-audit-kskn26 <repo> mily && cd mily
bash deploy/vps-setup.sh
```

Скрипт **сначала проверяет, достучится ли машина до фида** (ожидается
`HTTP 101`), и только потом ставит окружение: venv, зависимости, классы
protobuf, все тесты. Смысл порядка простой — машина, которая не может открыть
сокет, не сможет записывать, как бы хорошо ни установилось всё остальное, и
узнать это лучше за десять секунд, а не после полной установки.

Дальше либо в `tmux`, либо службой:

```bash
sudo cp deploy/betboom-capture.service /etc/systemd/system/
# заменить __ROOT__ и __USER__ — скрипт печатает готовую команду sed
sudo systemctl enable --now betboom-capture
journalctl -u betboom-capture -f
```

Юнит перезапускается всегда и без лимита попыток: рекордер переподключается
сам, поэтому падение процесса означает, что он умер по-настоящему. Запись,
которая осталась лежать, — единственный отказ, который стоит данных навсегда.

**Диск.** 0.3–0.9 ГБ в сутки на десять матчей, измерено. Месяц — 10–27 ГБ.
Проверить свободное место до того, как оставлять без присмотра.

**Сам юнит тестами не покрыт** — покрыт рекордер. Юнит-файл кодирует только
эксплуатационное намерение, и проверяется он первым запуском на месте.

### Что рекордер не подписывает

В дереве тенниса BetBoom, измерено на живом снимке, **12 из 32 турниров** — не
то, что нужно модели подачи: 11 парных («Пары» в названии) и один симулятор
(`ESportsBattle eTennis`, категория «Кибертеннис»). При `--max-matches 10` они
занимали слоты, предназначенные одиночным матчам.

Рекордер их **не подписывает** — но всё, что фид присылает сам, по-прежнему
ложится на диск сырым; правило «байты раньше суждений» не нарушено. Отчёт при
выходе перечисляет пропущенные турниры и причину. Вернуть: `--include-doubles`,
`--include-sim`.

### Как узнать, что запись жива, не заходя на машину

Отказ, который важен, — **тихий**: процесс умер, или сокет отвалился и не
вернулся, и никто об этом не сказал. Гейм-рынок исчезает через минуту после
котировки, так что ночь молчания — потерянная навсегда ночь.

Сама машина об этом и сообщает. `tennis/ingest/status.py` отвечает на один
вопрос по файлам на диске — пишет ли запись прямо сейчас:

```bash
python -m tennis.ingest.status data/raw
```

Ничего не распаковывает: размер и время изменения свежего лога — достаточный
признак, потому что живая запись трогает файл каждые несколько секунд, а
мёртвая не трогает никогда. Код выхода 0, если всё хорошо, 1 если нет. Свободное
место показывается **в днях записи**, а не в байтах: это то число, по которому
принимают решение.

`deploy/heartbeat-push.sh` публикует этот отчёт в отдельную ветку
`capture-status`, по файлу на машину (`status/<hostname>.json`). В cron:

```
*/5 * * * * cd /path/to/capture && bash deploy/heartbeat-push.sh >> /tmp/hb.log 2>&1
```

Проверено от начала до конца: ветка создаётся с нуля, содержит **только**
файлы статуса, повторные записи обновляют её, конфликт между машинами
разрешается перебазированием (файлы не пересекаются).

**Про доступ.** Публикация требует прав на запись с машины записи. Ключ
развёртывания, ограниченный одним этим репозиторием, а не личный токен с
доступом ко всему аккаунту: машина стоит без присмотра, и её единственная
работа — дописывать статус.

**Потеря при падении ограничена интервалом `fsync`** — по умолчанию одна
секунда. Дозапись не усекает файл, оборванный gzip-член читается до места
обрыва, так что упавший процесс стоит секунды, а не дня.

## Как воспроизвести

```bash
# 1. схема из бандла (имя файла меняется при каждом деплое)
#    взять vendor-core-*.js из
#    https://sportbook.sporthub.bet/widgets/sportbook/v1/modern/
python tennis/ingest/betboom/extract_schema.py vendor-core-*.js \
    -o tennis/ingest/betboom/proto

# 2. сгенерировать классы
pip install grpcio-tools websockets
mkdir -p tennis/ingest/betboom/generated      # protoc сам его не создаёт
python -m grpc_tools.protoc -I tennis/ingest/betboom/proto \
    --python_out=tennis/ingest/betboom/generated \
    tennis/ingest/betboom/proto/bb_sport_ws_v1.proto

# 3. первая живая сессия — разведка
python -m tennis.ingest.betboom.client --discover --max-matches 3

# 4. запись
python -m tennis.ingest.betboom.client --out data/raw --max-matches 8
```

`APP_BUILD` в `runtime-env.js` стоит сверять перед каждым запуском: номера полей
это контракт, и молчаливая перенумерация испортит запись, не подняв ошибки.

Разбор записанного лога, когда что-то пошло не так:

```bash
python -m tennis.ingest.betboom.inspect_log data/raw
```

Он классифицирует каждый кадр, показывает отправленные запросы рядом с
ответами, печатает структуру первого кадра каждого типа через рефлексию
protobuf и распаковывает детали ошибок — включая имя поля, которое сервер
отверг.
